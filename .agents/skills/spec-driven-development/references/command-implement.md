# Implement — execute the task list phase by phase

Ported from spec-kit `templates/commands/implement.md` at commit
`c43849408ac0de2ca6a52f14eaae71449776057b`; see [upstream.md](upstream.md).

Execute the implementation plan by processing and executing all tasks defined in
`tasks.md`, respecting dependencies and parallel markers. Read this file only when
running the implement step.

## Outline

1. Resolve the feature paths and the available documents:

   ```bash
   python scripts/sdd_workflow.py --action prereqs --require-tasks --json
   ```

   Parse `FEATURE_DIR`, `TASKS`, and the `AVAILABLE_DOCS` list. All paths must be
   absolute for filesystem operations.

2. **Check checklist status** when `<FEATURE_DIR>/checklists/` exists:
   - Treat checklist markers as a read-only gate: scan checkbox state, report
     status, and ask before proceeding when needed. Do NOT modify checklist files
     or markers.
   - `checklists/requirements.md` is the built-in spec-quality checklist maintained
     by the specify and clarify steps; custom checklists generated by the checklist
     step are reviewer-owned requirements-quality review artifacts.
   - For custom checklists, `[x]` means the reviewer determined the
     requirements-quality criterion is satisfied; it does NOT mean implementation
     work is complete.
   - Scan all checklist files in the directory. For each checklist count: total
     items (lines matching `- [ ]`, `- [X]`, or `- [x]`), checked items (lines
     matching `- [X]` or `- [x]`), and unchecked items (lines matching `- [ ]`).
   - Create a status table:

     ```text
     | Checklist | Total | Checked | Unchecked | Status |
     |-----------|-------|---------|-----------|--------|
     | ux.md     | 12    | 12      | 0         | PASS   |
     | test.md   | 8     | 5       | 3         | FAIL   |
     | security.md | 6   | 6       | 0         | PASS   |
     ```

   - Calculate the overall status: PASS when all checklists have zero unchecked
     items; FAIL when one or more checklists have unchecked items.
   - **When any checklist has unchecked items**: display the table, then **STOP**
     and ask: "Some checklists have unchecked items. Do you want to proceed with
     implementation anyway? (yes/no)". Wait for the answer. If the user says "no",
     "wait", or "stop", halt. If the user says "yes", "proceed", or "continue",
     continue with step 3.
   - **When all checklists are checked**: display the table showing all checklists
     passed, then continue with step 3 automatically.

3. Load and analyze the implementation context:
   - **REQUIRED**: read `tasks.md` for the complete task list and execution plan.
   - **REQUIRED**: read `plan.md` for the stack, architecture, and file structure.
   - **IF EXISTS**: read `data-model.md` for entities and relationships.
   - **IF EXISTS**: read `contracts/` for interface specifications and test
     requirements.
   - **IF EXISTS**: read `research.md` for technical decisions and constraints.
   - **IF EXISTS**: read `.specify/memory/constitution.md` for governance
     constraints.
   - **IF EXISTS**: read `quickstart.md` for integration scenarios.

4. **Project setup verification**: create or verify ignore files based on the
   detected stack. Check whether the directory is a git repository and verify
   `.gitignore` when it is; add `.dockerignore` when Docker is in the plan; add
   `.eslintignore` or update the config `ignores` when a linter config exists; add
   `.prettierignore` for a formatter config; add `.npmignore` when publishing an
   npm package; add `.terraformignore` for Terraform and `.helmignore` for Helm.
   When an ignore file already exists, verify it covers the essential build and
   cache output for the stack and append only the missing critical patterns. When
   it is missing, create it with the full pattern set for the detected technology.

5. Parse the `tasks.md` structure and extract:
   - Task phases: setup, tests, core, integration, polish.
   - Task dependencies: sequential versus parallel execution rules.
   - Task details: id, description, file paths, parallel markers [P].
   - Execution flow: order and dependency requirements.

6. Execute implementation following the task plan:
   - **Phase-by-phase**: complete each phase before moving to the next.
   - **Respect dependencies**: run sequential tasks in order; parallel tasks [P]
     may run together.
   - **Follow the test-first approach**: execute test tasks before their
     corresponding implementation tasks when tests were requested.
   - **File-based coordination**: tasks affecting the same file run sequentially.
   - **Validation checkpoints**: verify each phase's completion before proceeding.

7. Implementation execution rules:
   - **Setup first**: initialize project structure, dependencies, configuration.
   - **Tests before code**: write contract, entity, and integration tests first
     when tests were requested.
   - **Core development**: implement models, services, CLI commands, endpoints.
   - **Integration work**: database connections, middleware, logging, external
     services.
   - **Polish and validation**: unit tests, performance optimization,
     documentation.

8. Progress tracking and error handling:
   - Report progress after each completed task.
   - Halt execution when a non-parallel task fails.
   - For parallel tasks [P], continue with successful tasks and report the failed
     ones.
   - Provide clear error messages with context for debugging.
   - Suggest next steps when implementation cannot proceed.
   - **IMPORTANT**: for completed tasks, mark the checkbox as `[X]` in `tasks.md`.

9. Completion validation:
   - Verify all required tasks are completed.
   - Check that the implemented features match the original specification.
   - Validate that tests pass and coverage meets requirements.
   - Confirm that the implementation follows the technical plan.

Note: this step assumes a complete task breakdown exists in `tasks.md`. When tasks
are incomplete or missing, suggest running the tasks step
([command-tasks.md](command-tasks.md)) first to regenerate the task list.
