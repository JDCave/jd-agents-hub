Ported from spec-kit `templates/commands/checklist.md` at commit
`c43849408ac0de2ca6a52f14eaae71449776057b`; see [upstream.md](upstream.md).

Read this file only when running the checklist step. The checklist step is an
optional quality gate and does not replace the built-in spec-quality checklist at
`checklists/requirements.md`.

## Checklist Purpose: "Unit Tests for English"

**CRITICAL CONCEPT**: checklists are **UNIT TESTS FOR REQUIREMENTS WRITING**. They
validate the quality, clarity, and completeness of the requirements in a given
domain.

**NOT for verification or testing**:

- NOT "Verify the button clicks correctly"
- NOT "Test error handling works"
- NOT "Confirm the API returns 200"
- NOT checking whether code or implementation matches the spec

**FOR requirements-quality validation**:

- "Are visual hierarchy requirements defined for all card types?" (completeness)
- "Is 'prominent display' quantified with specific sizing or positioning?"
  (clarity)
- "Are hover-state requirements consistent across all interactive elements?"
  (consistency)
- "Are accessibility requirements defined for keyboard navigation?" (coverage)
- "Does the spec define what happens when a logo image fails to load?" (edge cases)

**Metaphor**: if the spec is code written in English, the checklist is its unit
test suite. It tests whether the requirements are well written, complete,
unambiguous, and ready for implementation, not whether the implementation works.

**Ownership and checkbox lifecycle**:

- Custom checklists generated by this step are reviewer-owned requirements-quality
  review artifacts.
- `[x]` means the reviewer determined the requirements-quality criterion is
  satisfied.
- `[x]` does NOT mean implementation work is complete.
- This step generates or appends checklist items; it MUST NOT mark generated items
  `[x]`.
- An agent may help evaluate items only when the reviewer explicitly asks.
- `checklists/requirements.md` is a separate built-in spec-quality checklist
  maintained by the specify and clarify steps. Do not treat that exception as
  applying to custom checklists generated here.

## Execution Steps

1. **Setup**: resolve the feature paths and the checklist template:

   ```bash
   python scripts/sdd_workflow.py --action prereqs --json
   python scripts/sdd_workflow.py --action resolve-template --template checklist-template --json
   ```

   Parse `FEATURE_DIR`, the `AVAILABLE_DOCS` list, and `TEMPLATE_CONTENT`. All
   file paths must be absolute for filesystem operations.

2. **IF EXISTS**: Load `.specify/memory/constitution.md` for project principles and
   governance constraints.

3. **Clarify intent dynamically**: derive up to THREE initial contextual
   clarifying questions, with no pre-baked catalog. They MUST:
   - Be generated from the user's phrasing plus extracted signals from spec, plan,
     and tasks.
   - Ask only about information that materially changes checklist content.
   - Be skipped individually when already unambiguous in the user's request.
   - Prefer precision over breadth.

   Generation algorithm:
   1. Extract signals: feature domain keywords (auth, latency, UX, API), risk
      indicators ("critical", "must", "compliance"), stakeholder hints ("QA",
      "review", "security team"), and explicit deliverables.
   2. Cluster signals into candidate focus areas (maximum 4), ranked by relevance.
   3. Identify the probable audience and timing (author, reviewer, QA, release)
      when not explicit.
   4. Detect missing dimensions: scope breadth, depth and rigor, risk emphasis,
      exclusion boundaries, measurable acceptance criteria.
   5. Formulate questions from these archetypes:
      - Scope refinement: "Should this include integration touchpoints with X and
        Y, or stay limited to local module correctness?"
      - Risk prioritization: "Which of these potential risk areas should receive
        mandatory gating checks?"
      - Depth calibration: "Is this a lightweight pre-commit sanity list or a
        formal release gate?"
      - Audience framing: "Will this be used by the author only, or by peers
        during review?"
      - Boundary exclusion: "Should we explicitly exclude performance tuning
        items this round?"
      - Scenario-class gap: "No recovery flows were detected. Are rollback and
        partial-failure paths in scope?"

   Question formatting rules:
   - When presenting options, generate a compact table with columns
     Option | Candidate | Why It Matters.
   - Limit to A-E options at most; omit the table when a free-form answer is
     clearer.
   - Never ask the user to restate what they already said.
   - Avoid speculative categories. If uncertain, ask explicitly: "Confirm whether
     X belongs in scope."

   Defaults when interaction is impossible:
   - Depth: Standard.
   - Audience: Reviewer for review-related work; Author otherwise.
   - Focus: the top 2 relevance clusters.

   Output the questions labelled Q1, Q2, Q3. After the answers, if two or more
   scenario classes (alternate, exception, recovery, non-functional domain) remain
   unclear, you MAY ask up to TWO more targeted follow-ups, Q4 and Q5, with a
   one-line justification each. Do not exceed five total questions. Skip
   escalation when the user explicitly declines more.

4. **Understand the user request**: combine the request with the clarifying
   answers:
   - Derive the checklist theme (security, review, deploy, UX).
   - Consolidate explicit must-have items mentioned by the user.
   - Map focus selections to category scaffolding.
   - Infer missing context from spec, plan, and tasks; do not invent content.

5. **Load feature context** from `FEATURE_DIR`:
   - `spec.md`: feature requirements and scope.
   - `plan.md` if it exists: technical details and dependencies.
   - `tasks.md` if it exists: implementation tasks.

   **Context loading strategy**:
   - Load only the portions relevant to the active focus areas; avoid dumping
     entire files.
   - Prefer summarizing long sections into concise scenario or requirement
     bullets.
   - Use progressive disclosure: fetch more only when a gap is detected.
   - When source documents are large, generate interim summary items instead of
     embedding raw text.

6. **Generate the checklist** using `TEMPLATE_CONTENT` as the structural template
   and write "Unit Tests for Requirements":
   - Create the `FEATURE_DIR/checklists/` directory when it does not exist.
   - Generate a unique checklist filename: a short, descriptive domain name such
     as `ux.md`, `api.md`, or `security.md`.
   - File handling:
     - If the file does NOT exist, create it and number items starting at CHK001.
     - If the file exists, append new items and continue from the last CHK id
       (if the last item is CHK015, new items start at CHK016).
   - Never delete or replace existing checklist content; always preserve and
     append.
   - Leave every newly generated item unchecked (`[ ]`); checkbox state belongs to
     the reviewer.

   **CORE PRINCIPLE: test the requirements, not the implementation.**
   Every checklist item MUST evaluate the requirements themselves for:
   - **Completeness**: are all necessary requirements present?
   - **Clarity**: are the requirements unambiguous and specific?
   - **Consistency**: do the requirements align with each other?
   - **Measurability**: can the requirements be objectively verified?
   - **Coverage**: are all scenarios and edge cases addressed?

   **Category structure**, grouping items by requirement-quality dimension:
   - Requirement Completeness
   - Requirement Clarity
   - Requirement Consistency
   - Acceptance Criteria Quality
   - Scenario Coverage
   - Edge Case Coverage
   - Non-Functional Requirements (performance, security, accessibility)
   - Dependencies and Assumptions
   - Ambiguities and Conflicts

   **Item structure**: each item is a question about requirement quality, focused
   on what is written or missing in the spec and plan, and carries a quality
   dimension in brackets, for example `[Completeness]`, `[Clarity]`, or
   `[Consistency]`. Reference the spec section (`[Spec §X.Y]`) when checking
   existing requirements and use `[Gap]` when checking for missing requirements.
   The canonical line format is:

   ```markdown
   - [ ] CHK001 Is the number and layout of featured episodes explicitly specified? [Completeness, Spec §FR-001]
   ```

   **Examples by quality dimension**:

   Completeness:
   - "Are error-handling requirements defined for all API failure modes? [Gap]"
   - "Are accessibility requirements specified for all interactive elements? [Completeness]"

   Clarity:
   - "Is 'fast loading' quantified with specific timing thresholds? [Clarity, Spec §NFR-2]"
   - "Is 'prominent' defined with measurable visual properties? [Ambiguity, Spec §FR-4]"

   Consistency:
   - "Do navigation requirements align across all pages? [Consistency, Spec §FR-10]"

   Coverage:
   - "Are requirements defined for zero-state scenarios? [Coverage, Edge Case]"
   - "Are requirements specified for partial data-loading failures? [Coverage, Exception Flow]"

   Measurability:
   - "Can 'balanced visual weight' be objectively verified? [Measurability, Spec §FR-2]"

   **Scenario classification and coverage**: check whether requirements exist for
   primary, alternate, exception and error, recovery, and non-functional
   scenarios. For each class ask: "Are requirements for this scenario class
   complete, clear, and consistent?" If a class is missing, ask whether it is
   intentionally excluded or missing, and tag `[Gap]`. Include resilience and
   rollback when state mutation occurs.

   **Traceability requirements**: at least 80 percent of items MUST include at
   least one traceability reference: a spec section `[Spec §X.Y]` or one of the
   markers `[Gap]`, `[Ambiguity]`, `[Conflict]`, or `[Assumption]`. When no id
   system exists, ask: "Is a requirement and acceptance-criteria id scheme
   established? [Traceability]".

   **Surface and resolve issues** by asking about the requirements themselves:
   ambiguities ("Is 'fast' quantified with specific metrics? [Ambiguity]"),
   conflicts ("Do navigation requirements conflict between §FR-10 and §FR-10a?
   [Conflict]"), assumptions ("Is the assumption of an always-available external
   API validated? [Assumption]"), dependencies ("Are external API requirements
   documented? [Dependency, Gap]"), and missing definitions ("Is 'visual hierarchy'
   defined with measurable criteria? [Gap]").

   **Content consolidation**:
   - Soft cap: when there are more than 40 raw candidate items, prioritize by risk
     and impact.
   - Merge near-duplicates that check the same requirement aspect.
   - When there are more than five low-impact edge cases, write one item: "Are
     edge cases X, Y, and Z addressed in requirements? [Coverage]".

   **PROHIBITED** patterns, which would make this an implementation test:
   - Any item starting with "Verify", "Test", "Confirm", or "Check" plus
     implementation behavior.
   - References to code execution, user actions, or system behavior.
   - "Displays correctly", "works properly", "functions as expected".
   - Words such as "click", "navigate", "render", "load", or "execute".
   - Test cases, test plans, or QA procedures.
   - Implementation details such as frameworks, APIs, or algorithms.

   **REQUIRED** patterns, which test requirements quality:
   - "Are [requirement type] defined, specified, or documented for [scenario]?"
   - "Is [vague term] quantified or clarified with specific criteria?"
   - "Are requirements consistent between [section A] and [section B]?"
   - "Can [requirement] be objectively measured or verified?"
   - "Are [edge cases or scenarios] addressed in requirements?"
   - "Does the spec define [missing aspect]?"

7. **Structure reference**: generate the checklist following the canonical template
   resolved from `assets/templates/checklist-template.md`: title, meta section,
   category headings, ownership note, notes section, and id formatting. Replace the
   template's sample rows and note placeholders with the generated items and the
   real ownership note. If the template is unavailable, use an H1 title, purpose
   and created meta lines, an ownership note explaining that `[x]` means reviewer
   approval of requirements quality, `##` category sections containing
   `- [ ] CHK### <requirement item>` lines with globally incrementing ids starting
   at CHK001, and notes stating that the implement step reads checklist state but
   does not modify the markers.

8. **Report**: output the full path to the checklist file, the item count, and
   whether the run created a new file or appended to an existing one. Summarize
   the focus areas selected, the depth level, the actor and timing, and any
   explicit must-have items the user supplied.

**Important**: each checklist invocation uses a short, descriptive checklist
filename and either creates a new file or appends to an existing one. This allows
multiple checklists of different types (`ux.md`, `test.md`, `security.md`), simple
memorable filenames that indicate purpose, and easy navigation in the
`checklists/` folder. To avoid clutter, use descriptive types and clean up
obsolete checklists when they are done.

## Example Checklist Types and Sample Items

**UX requirements quality** (`ux.md`):

- "Are visual hierarchy requirements defined with measurable criteria? [Clarity, Spec §FR-1]"
- "Is the number and positioning of UI elements explicitly specified? [Completeness, Spec §FR-1]"
- "Are interaction-state requirements (hover, focus, active) consistently defined? [Consistency]"
- "Are accessibility requirements specified for all interactive elements? [Coverage, Gap]"
- "Is fallback behavior defined when images fail to load? [Edge Case, Gap]"

**API requirements quality** (`api.md`):

- "Are error-response formats specified for all failure scenarios? [Completeness]"
- "Are rate-limiting requirements quantified with specific thresholds? [Clarity]"
- "Are authentication requirements consistent across all endpoints? [Consistency]"
- "Are retry and timeout requirements defined for external dependencies? [Coverage, Gap]"
- "Is the versioning strategy documented in requirements? [Gap]"

**Performance requirements quality** (`performance.md`):

- "Are performance requirements quantified with specific metrics? [Clarity]"
- "Are performance targets defined for all critical user journeys? [Coverage]"
- "Can performance requirements be objectively measured? [Measurability]"
- "Are degradation requirements defined for high-load scenarios? [Edge Case, Gap]"

**Security requirements quality** (`security.md`):

- "Are authentication requirements specified for all protected resources? [Coverage]"
- "Are data-protection requirements defined for sensitive information? [Completeness]"
- "Is the threat model documented and are requirements aligned to it? [Traceability]"
- "Are security requirements consistent with compliance obligations? [Consistency]"
- "Are security failure and breach-response requirements defined? [Gap, Exception Flow]"

## Anti-Examples: What NOT To Do

Wrong, because these test implementation instead of requirements:

```markdown
- [ ] CHK001 - Verify landing page displays 3 episode cards [Spec §FR-001]
- [ ] CHK002 - Test hover states work correctly on desktop [Spec §FR-003]
- [ ] CHK003 - Confirm logo click navigates to home page [Spec §FR-010]
- [ ] CHK004 - Check that related episodes section shows 3-5 items [Spec §FR-005]
```

Correct, because these test requirements quality:

```markdown
- [ ] CHK001 - Are the number and layout of featured episodes explicitly specified? [Completeness, Spec §FR-001]
- [ ] CHK002 - Are hover state requirements consistently defined for all interactive elements? [Consistency, Spec §FR-003]
- [ ] CHK003 - Are navigation requirements clear for all clickable brand elements? [Clarity, Spec §FR-010]
- [ ] CHK004 - Is the selection criteria for related episodes documented? [Gap, Spec §FR-005]
- [ ] CHK005 - Are loading state requirements defined for asynchronous episode data? [Gap]
- [ ] CHK006 - Can "visual hierarchy" requirements be objectively measured? [Measurability, Spec §FR-001]
```

Key differences:

- Wrong: tests whether the system works correctly. Correct: tests whether the
  requirements are written correctly.
- Wrong: verification of behavior. Correct: validation of requirement quality.
- Wrong: "Does it do X?" Correct: "Is X clearly specified?"

- [ ] Report emitted with path, item count, focus areas, and depth level
