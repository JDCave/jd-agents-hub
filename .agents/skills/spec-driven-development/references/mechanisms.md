# Cross-cutting mechanisms

This file collects the rules that span more than one step: the process order,
which steps are optional, the constitution authority, the clarification economy,
checklist ownership, the read-only analyze rule, the append-only converge rule,
the `.specify/` artifact contract, and the exact script contract used by every
command reference.

## 1. Process order and optional gates

The canonical order is:

```text
constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge
```

- Only `specify` is strictly required before `plan`.
- `clarify`, `checklist`, and `analyze` are optional quality gates; add them
  whenever the feature carries meaningful ambiguity or risk.
- `converge` repeats after each `implement` pass that appended tasks, until it
  reports converged.
- Branch, commit, and pull-request lifecycle is not part of this skill. Use the
  hub's change-ticket workflow for that.

## 2. Constitution authority

`.specify/memory/constitution.md` is the highest authority in the process. It is
read by the specify, clarify, plan, tasks, checklist, analyze, converge, and
implement steps. It is a hard gate in `plan` (Constitution Check before Phase 0 and
a re-check after Phase 1; an unjustified violation is an ERROR, a justified one
goes in the Complexity Tracking table), automatically CRITICAL in `analyze`, and
the highest-priority finding class in `converge`. Changing a principle is a
separate, explicit constitution step; no other step may reinterpret or dilute it.

## 3. NEEDS CLARIFICATION economy

- `specify`: at most **3** `[NEEDS CLARIFICATION: ...]` markers. Priority order is
  scope > security/privacy > UX > technical details. Everything else becomes an
  informed guess recorded under Assumptions.
- `plan`: every unknown in Technical Context is marked `NEEDS CLARIFICATION` and
  must be resolved by Phase 0 research; an unresolved item at the end is an ERROR.
- `clarify`: at most **5** questions in total, encoded back into `spec.md` with a
  coverage summary that marks each category Resolved, Deferred, Clear, or
  Outstanding.

## 4. Checklist ownership (three distinct objects)

1. **Built-in spec-quality checklist** at
   `<feature_dir>/checklists/requirements.md`: created and maintained by `specify`
   and re-evaluated by `clarify` only.
2. **Custom requirements-quality checklists** at
   `<feature_dir>/checklists/<domain>.md`: generated by `checklist`, reviewer-owned.
   `[x]` means the reviewer judged the requirements-quality criterion satisfied; it
   does not mean implementation is complete. The checklist step never marks items
   `[x]`; an agent may evaluate them only when the reviewer explicitly asks.
3. **Implementation checkbox state**: `implement` reads checklist state as a gate
   and asks before proceeding when unchecked items exist. It never edits checklist
   markers; it marks only `tasks.md` checkboxes `[X]`.

## 5. Analyze is read-only

`analyze` never modifies files. It reports a findings table with ids, category,
severity, location, summary, and recommendation, plus a coverage summary, metrics,
and Next Actions. Severity is CRITICAL, HIGH, MEDIUM, or LOW with the heuristics in
[command-analyze.md](command-analyze.md). Findings cap at 50, with an overflow
summary. Remediation is offered only and applied manually after explicit approval.

## 6. Converge is append-only

`converge` has exactly one possible write: a new `## Phase N: Convergence` section
appended to `tasks.md`. It never modifies `spec.md` or `plan.md`, never renumbers,
reorders, or deletes tasks, and never touches code. When everything is satisfied,
`tasks.md` stays byte-for-byte unchanged and no empty header is written. Each
appended task is traceable, for example
`- [ ] T042 <imperative description> per <source-ref> (<gap-type>)`, where the gap
type is `missing`, `partial`, `contradicts`, or `unrequested`.

## 7. The `.specify/` artifact contract

```text
<project root>/
├── .specify/
│   ├── memory/
│   │   └── constitution.md        # seeded once from the bundled constitution template
│   ├── templates/                 # optional project overrides of the page templates
│   └── feature.json               # {"feature_directory": "specs/NNN-name"}
└── specs/
    └── NNN-feature-name/
        ├── spec.md                # specify
        ├── plan.md                # plan
        ├── tasks.md               # tasks; implement and converge update checkboxes/append
        ├── research.md            # plan Phase 0
        ├── data-model.md          # plan Phase 1, when data is involved
        ├── contracts/             # plan Phase 1, when interfaces exist
        ├── quickstart.md          # plan Phase 1
        └── checklists/
            ├── requirements.md    # built-in spec-quality checklist
            └── <domain>.md        # custom requirements-quality checklists
```

Rules the commands depend on:

- The project root is the directory that holds `.specify/`. The workflow script
  treats the positional target as that root; a file argument resolves to its parent
  folder.
- `.specify/feature.json` is the current-feature pointer and is rewritten on every
  feature switch. Commands never rely on branch names to locate the feature.
- `bootstrap` is idempotent: it creates `.specify/memory` and `.specify/templates`,
  and seeds `memory/constitution.md` only when the file is missing.
- Numbering is sequential: `new-feature` scans `specs/` for the highest
  three-or-more-digit prefix and allocates the next number. Timestamp-style names
  are ignored. The `--number` override bumps to the next free number with a
  warning when the requested number is taken.
- Slugs are lowercase kebab-case, at most 64 characters. A path separator or a
  parent segment in a requested slug is rejected.

## 8. Script contract (what replaced each spec-kit script invocation)

All command references call one standard-library entry point, relative to the skill
folder. Every action prints one compact JSON object with `--json` (ASCII-safe) and
one line per item without it. Exit codes are 0 for success and 2 for bad input or a
missing prerequisite.

| need | command |
|---|---|
| create the `.specify/` skeleton | `python scripts/sdd_workflow.py --action bootstrap --json` |
| allocate a feature and seed `spec.md` | `python scripts/sdd_workflow.py --action new-feature --title "..." --json` |
| resolve feature paths and available docs | `python scripts/sdd_workflow.py --action prereqs [--require-spec] [--require-tasks] --json` |
| seed `plan.md` from the template | `python scripts/sdd_workflow.py --action plan --json` |
| seed `tasks.md` from the template | `python scripts/sdd_workflow.py --action tasks --json` |
| resolve a page template | `python scripts/sdd_workflow.py --action resolve-template --template NAME --json` |
| summarize the workspace | `python scripts/sdd_workflow.py --action status --json` |

`plan` and `tasks` refuse to overwrite an existing artifact unless `--force` is
passed. `resolve-template` accepts `constitution-template`, `spec-template`,
`plan-template`, `tasks-template`, and `checklist-template`; an unknown name exits
2. `prereqs` resolves the feature directory from `.specify/feature.json` first, then
from the newest `specs/*/spec.md`. Output paths are project-relative with forward
slashes, so reports are portable across machines.

## 9. Template resolution precedence

1. Project override: `.specify/templates/<name>.md`.
2. Bundled asset: `assets/templates/<name>.md`.

The command must write **resolved** content, not a guessed file on disk. Preset and
extension composition layers are not ported, so the precedence has exactly two
levels.

## 10. Not ported (dropped platform mechanisms)

Dropped deliberately; their absence is intentional, not a missing TODO:

- Extension hooks (`hooks.before_*` / `hooks.after_*` in `.specify/extensions.yml`)
  and the hook runtime. Every command reference replaces the upstream pre- and
  post-execution sections with the pointer that appears at the end of that file.
- The `specify` CLI: `init`, `check`, `version`, `integration`, `extension`,
  `preset`, `workflow`, `bundle`, and `self` commands.
- The integration dispatch layer, per-agent renderers, and command-name
  placeholders.
- Presets and their replace/prepend/append/wrap composition strategies.
- Bundles, the workflow engine, extension catalogs, and event plumbing.
- The git extension, GitHub issue export, agent-context updates, and the selftest
  extension. Branch, commit, and pull-request lifecycle stays with the hub's
  change-ticket workflow.
- Timestamp-based feature numbering; only sequential numbering is ported.

The process content that survived is the command order, the gates, the caps, the
artifact schemas, the ids, and the error conditions. See [upstream.md](upstream.md)
for provenance and the full drop list.
